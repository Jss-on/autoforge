# Rollout, compatible recovery and operations

Before observation, pin a policy in the existing shipment/run record: target, immutable artifact, configuration SHA-256, pin timestamp, strategy (`staged` or `all-at-once`), maximum observed exposure (0..1), observation duration, minimum journey samples, maximum error fraction, p95 latency limit and evidence freshness. No telemetry or too few observations means HOLD. Averages cannot hide failure spikes through a lowered required-check target.

Collect actual timestamped unique journey samples with success and latency, start/end time, exposure, target/artifact/configuration identities and the policy's SHA-256 (`JSON.stringify(policy)`). The protected observer owns this data; a candidate-authored JSON file is not trusted telemetry. `node scripts/operational.cjs rollout policy.json observations.json` computes CONTINUE/HOLD with exit 0/1; malformed input exits 2. Vercel promotion uses this same gate and requires the observation inside the action-bound request. The synthetic pilot observes at zero customer exposure, then uses separately authorized all-at-once promotion. It does not assume provider canaries are available.

Pin recovery action (`rollback`, `forward`, or `maintenance`), owner, next drill time, RTO seconds and RPO seconds. Application rollback needs a fresh protected CI job named `Recovery compatibility`, with the old application tested on the current schema and the new application tested on preserved old data. Bind the current schema digest in policy/request and the protected verifier inputs. The migration principal alone changes schema; application credentials cannot execute DDL. Serialize migrations, deployment and recovery in the same native target workflow. Re-observe database schema/configuration identity before exposure; drift requires new compatibility execution. Use expand/contract changes; destructive down migrations are not an automatic recovery strategy. If old code cannot read the new schema, select and test forward/maintenance recovery instead.

For a restore drill, use synthetic data and a distinct database/branch destination. Measure from impact/failure start until the restored service actually answers its verified journey; copying a backup is not the end of RTO. RPO is the difference between impact time and the latest verified committed data recovered. Collect expected/actual row counts and canonical-content digests, compatibility outcomes, observed serving artifact, owner and next drill date. Run `node scripts/operational.cjs recovery policy.json restore.json`; only RECOVERED passes. These calculations validate measured inputs, not the authenticity of self-reported booleans; the protected drill executor must run the real data queries and compatibility checks and retain its Phase 2 execution/CI receipts.

The local SQLite fixture executes expansion, old/new readers, backup, simulated data loss and isolated restore. It guards harness mechanics, not Neon PostgreSQL compatibility or provider RTO/RPO. The selected Neon pilot must repeat the drill on its actual managed database within its verified history-retention window, observing provider operation IDs, data point and service usability. Never restore over a customer/source branch merely to complete the drill.

Vercel rollback shares the same native concurrency, target, request authorization, durable journal and current-deployment check as promotion. Retain the known-good deployment during the rollback window. After timeout or cancellation, reconcile the recorded provider operation; never replace a newer deployment with a stale recovery request.

## Journey SLO and safe alert

Pin `slo: {target, window_ms, owner, telemetry, alert_sink, runbook, review_at}` in the approved delivery policy. `operational.cjs budget` reports SLI, sample count, coverage, remaining allowed failures and burn rate. No events or incomplete coverage means HOLD; exhausted budget means REPAIR_ONLY. A short observation may validate mechanics and allow a healthy pilot promotion, while `slo_proven` remains false until the full window is observed. Emergency recovery still needs normal authorization and fresh compatibility; it is not a blanket gate bypass.

`operational.cjs observe <rollout-policy> <origin> <output>` executes bounded authenticated create/read probes. Pin `observation_origin` and the actual deployment/configuration identity. HTTPS is required except explicitly identified loopback fixtures. Its optional `test_alert_url` accepts loopback HTTP only and requires a real sink acknowledgement. Use provider-native alerting for real responders under separately authorized scope. Distinguish dependency readiness (503 when unavailable) from process liveness (200); do not restart a healthy process because its database is down. Retain collector output, sink receipt and the exercised runbook steps. Schedule the full-window review by setting its actual future date/owner; never claim a month-long SLO from this short pilot.
